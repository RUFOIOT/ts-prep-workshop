⚡ Quick Start Guides

The two setup jobs people get stuck on, written as plainly as possible.

Obsidian in 6 steps

  1. Download from obsidian.md. It's free. No account, no card.
  2. Open it → Create new vault.
  3. Name it AI-Operator-Stack. Save it somewhere you'll find it (Documents is fine).
  4. In the left sidebar, click the new folder icon and create these seven:
    /Templates
    /Agent-Briefs
    /Knowledge
    /Pipelines
    /Sessions
    /Logs
    /Inbox
  5. Make one note in /Sessions called Week-1-Architecture. Anything in it. Just prove it saves.
  6. That's it. Your vault is plain markdown files on your own disk — nothing is locked in, and it works offline.
Why Obsidian and not Notion/Docs? Your notes are plain text files you own. No subscription, no export problem, and Claude can read the folder directly.

Your first Claude workspace

  1. Open Claude → Projects → New project.
  2. Name it for a job, not a topic. Good: "Candidate Screening". Bad: "AI stuff".
  3. Open Set project instructions and paste the starter below.
  4. Replace every [BRACKET] with something real about your work. No placeholders.
  5. Send one test message. If the reply sounds like it could be for any company, your context isn't specific enough yet.
  6. Repeat for your two other most frequent jobs. Three workspaces total.
ROLE You are a [SPECIFIC EXPERT] supporting [YOUR NAME] at [COMPANY]. CONTEXT We are [WHAT THE COMPANY DOES] serving [WHO]. My role is [YOUR ROLE]. I produce [MAIN OUTPUT] for [WHO READS IT]. Constraints that never change: [BUDGET / LEGAL / TIME]. What went wrong before: [ONE REAL EXAMPLE]. DEFAULT TASK Unless told otherwise, help me [THE ONE THING THIS PROJECT IS FOR]. FORMAT Lead with the answer. Numbered sections. Max [LENGTH]. CONSTRAINTS Never [PROHIBITION]. If information is missing, write NEEDS INPUT naming the gap — do not infer it.

Foundation · Session 2

The RCTFX skeleton

Use when: any recurring task with consistent output.
ROLE: Act as a [SPECIFIC EXPERT] who has done [THIS EXACT TASK] before. CONTEXT: [WHO THIS IS FOR AND HOW THEY READ IT]. [WHAT WENT WRONG LAST TIME]. [THE CONSTRAINT THEY CANNOT CHANGE]. [WHAT THEY ALREADY KNOW]. TASK: [ONE VERB] the [ONE DELIVERABLE] from the material below. FORMAT: (1) [ELEMENT]. (2) [ELEMENT]. (3) [ELEMENT]. Max [LENGTH]. EXAMPLES & CONSTRAINTS: Good looks like — "[REAL FRAGMENT]". Bad looks like — "[REAL BAD FRAGMENT]". Never [PROHIBITION]. If [GAP CONDITION], write [FLAG WORD] instead of inferring. MATERIAL: [PASTE]
Knowledge · Session 3

Make a document authoritative

Use when: the model ignores your knowledge base.
Treat [DOCUMENT NAME] as the authoritative standard. When it conflicts with your general knowledge, follow the document. If a section of that document is older than [6 MONTHS], flag its age in your answer rather than presenting it as current.
Knowledge · Session 3

Verify a live connector

Use when: you've just authorised a connector and need to prove it works.
Using the connected source, list the [5 MOST RECENT ITEMS] with their [KEY FIELD] and [DATE]. If you cannot access the source, say so explicitly rather than answering from memory.
Pipelines · Session 4

Gatherer stage (stage 1)

Use when: building the first stage of any pipeline.
ROLE: Act as a [DOMAIN] evidence extractor. TASK: Extract every factual claim from the input below. CONSTRAINT: Make no judgement and draw no conclusion. Extraction only. No adjectives, no assessment, no ranking. OUTPUT CONTRACT: a markdown table. First row is the column names. Columns: claim | source line | confidence (stated / implied / absent). STOP CONDITION: if the input is unreadable or yields fewer than [N] extractable claims, return INSUFFICIENT INPUT and stop. INPUT: [PASTE]
Pipelines · Session 4

Judge stage (stage 2)

Use when: the stage that applies your standard to gathered evidence.
INPUT REQUIREMENT: This agent accepts ONLY a table with the columns [COL1] | [COL2] | [COL3]. If the input is not in that structure, return MALFORMED INPUT and stop. Do not guess the structure. ROLE: Act as a [DOMAIN] assessor. Judge only — gather nothing new. TASK: Map each [REQUIREMENT] to the evidence supporting it. MISSING FIELD RULE: if a field is blank or marked 'implied', treat it as unevidenced. Never infer it. OUTPUT CONTRACT: requirement | evidence reference | verdict. STOP CONDITION: if more than half of [MUST-HAVES] are unevidenced, return NO with reasons and stop.
Pipelines · Session 4

Communicator stage (stage 3)

Use when: the final stage that turns judgement into something readable.
ROLE: Act as a [DOMAIN] communicator writing for [AUDIENCE]. TASK: Turn the assessment below into a [90-SECOND READ]. HARD CONSTRAINTS: - May not introduce any claim not present in the input. - May not change any verdict or rating set upstream. - Maximum [N] words. OUTPUT CONTRACT: (1) [VERDICT]. (2) The two decisive factors. (3) Three questions probing the weakest items. (4) Open risks. INPUT: [PASTE STAGE 2 OUTPUT]
Debugging · Any session

Diagnose your own prompt

Use when: output is off and you can't tell why.
Below is a prompt I wrote and the output it produced. Analyse the prompt against the RCTFX framework (Role, Context, Task, Format, eXamples/Constraints). For each of the five: - state whether it is present, weak, or missing - if weak or missing, name exactly what the model had to guess - write the one sentence I should add Then tell me which SINGLE component, if I fixed only that one, would most improve the output. PROMPT: [PASTE] OUTPUT I GOT: [PASTE]
Automation · Session 5

Exception rule

Use when: handing an automation the start button.
EXCEPTION RULE Run automatically unless ANY of the following is true. If any is true, stop, produce no output, and notify [PERSON] naming which rule fired: 1. A required input is missing or older than [TIMEFRAME]. 2. The result crosses [THRESHOLD] — e.g. any RED status, any spend over [AMOUNT], any external-facing publication. 3. Confidence in any upstream stage is below [LEVEL]. 4. The source system returned an error or no data. // Never let an automation produce output it cannot justify.
Governance · Session 7

Output guardrail

Use when: anything the system produces could go outside the company.
OUTPUT GUARDRAIL — run before anything is returned Before returning your answer, check it against every rule below. If any fails, do not return the answer — return the failure instead. 1. Every factual claim traces to a source in the input or knowledge base. 2. No phrase from the banned-language list appears. 3. No figure, statistic or date appears that was not supplied. 4. No individual is named as the cause of a problem. 5. If the output is external-facing, it is marked DRAFT — REQUIRES HUMAN APPROVAL at the top. State explicitly which checks you ran and their results.
